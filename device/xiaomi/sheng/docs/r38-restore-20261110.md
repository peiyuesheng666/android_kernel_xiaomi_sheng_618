# Restore the retained r38 device-tree images

The user requested restoring the latest device-tree images on ca10ede3/sheng
on 2026-11-10, then continuing face enrollment/unlock work. The tablet ran
HyperOS OS3.0.303.0.WNXCNXM on A with 6.18.32. Both super metadata copies showed
empty B logical partitions, requiring a complete installation.

The HyperOS physical boot chain was backed up under
artifacts/stock-before-r38-20261110. The complete set combines retained r30
boot/product/system_ext/DLKM inputs, r32 system/vbmeta_system, r36 ODM and r38
vendor. All fourteen image hashes passed. Initial AVB verification identified
stale init_boot and recovery descriptors in r38's root. The restore root changes
exactly those two descriptors to cover the complete retained debug images.
Public key, signature algorithm, flags (3), rollback fields, release string and
all other descriptors were preserved. Full AVB chain verification then passed.
The repaired root SHA256 is
b744a9853c080672f2f906b12e12a32449dfddbd4a82215c49167c16e74b0fe7.

The helper checked the stock fingerprint, unlocked state, serial, product and
slot. Seven logical partitions were written in fastbootd, shrinking product
first to release super space. Seven physical partitions were written in the
bootloader. All writes and reboot returned OKAY. Physical readback matches all
seven hashes. Firmware was not flashed. The initial flash retained userdata
and metadata.

Both Android startup attempts returned to recovery with
`--prompt_and_wipe_data --reason=init_user0_failed`. This is failed Android
startup, not an accepted restore. The agent did not accept the reset prompt.
Stock and retained vendor_boot encryption options match; stock also declares
a MIFS filesystem fallback. Recovery cannot mount raw encrypted userdata as
ordinary F2FS, which alone does not identify the Android user-0 failure.
The user then explicitly authorized clearing data and continuing startup
verification. Standard recovery `--wipe_data` was requested through the BCB,
preserving the A/B boot-control bytes. Recovery cleared data/metadata and Android
successfully booted, with sys.boot_completed=1 and SELinux Enforcing. All seven
logical image hashes and both vbmeta image-length prefixes match the restored
set. Original SystemUI SHA256 remains
33017b0d59e28da5db3e089a98f49601de508228a012392ee2d04c82cda3ccb1.
Both health services registered before ADB root was enabled; framework PIDs
remained stable during the observed startup period. These checks establish
restoration and basic startup, not face enrollment/unlock acceptance.

Raw evidence stays outside Git under reports/device/r38-restore-20261110:
manifest, AVB output, operation log, recovery logs, ramdisk comparison and
physical-readback.json. The restored control kernel is 5.15.220. The user's
future 6.18 partition-based module target is in KERNEL618_ANDROID_INTEGRATION.md.

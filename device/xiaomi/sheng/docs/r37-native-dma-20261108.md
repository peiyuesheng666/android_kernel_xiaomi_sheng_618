# Native DMA heaps for protected camera buffers

The pinned current system/memory/libdmabufheap source has removed ION support.
MapNameToIonHeap returns zero without registering mappings; the legacy Alloc
overload ignores ION flags and allocates directly from the named DMA heap.
The public Qualcomm gralloc chooses DmaLegacyManager when the native-DMA
property is absent. Its protected camera allocations select qcom,display with
ION flags 0x80200000 or 0x88200000, and its SecureMemPerms is a no-op. This cannot
convey the required camera and camera-preview VM permissions on this platform.

Set vendor.gralloc.use_dma_buf_heaps=true in the device vendor properties. The
existing DmaManager allocates the same heap and explicitly lends the buffer to
qcom,cp_camera with read/write and, for preview, qcom,cp_camera_preview with read.
No biometric strength, authentication-token checks, secure capture mode,
public library, SystemUI or kernel module is changed.

The device-owned diagnostic directly exercised both native secure allocation
cases under the su diagnostic domain. Allocation, LendDmabuf and release all
returned zero. It opened no camera, acquired no image and mapped no protected
pixels. This establishes the native backend and kernel interface, but does not
by itself certify allocator-domain permissions or working face enrollment.
The first diagnostic build omitted the exported color metadata include path;
the corrected second build passed. See the separate build and runtime reports.

The property assembly retains every existing vendor build.prop byte and adds
only the native-DMA property. Current platform property validation passed.
Fresh pre/post source audits passed for 25 public repositories and all 1243
project statuses. The r37 package independently read back the vendor filesystem
and changed only build.prop, preserving metadata and the filesystem UUID. AVB
signature and other parent descriptors passed verification. Full product and
normal product module builds remain uncompleted.

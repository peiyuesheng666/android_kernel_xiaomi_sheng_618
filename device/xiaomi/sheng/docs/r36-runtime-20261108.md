# r36 face runtime

The guarded postboot verification on ca10ede3/b passed seven partition hashes,
both policy payloads, all three Settings face preview resources and original
SystemUI. SELinux remained Enforcing. Evidence: reports/device/r36-20261108-132149.

The user still reported a black preview and confirmed spontaneous rebooting.
Two subsequent attempts were captured on the host, with the second capturing
both logcat and the kernel continuously. Camera 1 opened successfully, gralloc
allocated its image-reader buffers and SecurePreviewVideo submitted its first
frame to the IFE/IPE pipeline. The former allocator lookup abort and relevant
SELinux denials did not appear in these captures. Logging then stopped abruptly
and the tablet rebooted. Face enrollment and authentication have not passed.

The new kernel capture confirms the front sensor started in secure mode. It
does not contain a kernel panic, secure-firmware fatal message or conclusive
fault stack. Pstore was empty; DropBox contained no new system-server Watchdog
record. Exact read-only snapshots of the oops and mtdblk partitions also did not
establish the fault. Do not classify this as a proven missing-module problem.

The investigation found an independent, concrete allocator incompatibility:
the installed current libdmabufheap retains MapNameToIonHeap only as a no-op and
ignores the deprecated ION flags passed to Alloc. The unset
vendor.gralloc.use_dma_buf_heaps property selects DmaLegacyManager, whose secure
camera branch relies on precisely those flags. Its SecureMemPerms does no work.
This leaves the required camera VM permissions unexpressed on the current
platform. The r37 diagnostic verifies the existing native DMA manager's actual
allocation, secure lend and release path without opening a camera.

Evidence: reports/device/r36-face-runtime-20261108/logcat-live-retry.txt,
logcat-live-second-retry.txt, kernel-live-second-retry.txt and
secure-heap-probe-runtime.txt. Raw logs and dumps remain excluded from Git.

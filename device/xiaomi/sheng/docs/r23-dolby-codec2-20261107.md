# r23 Dolby Codec2 service allocation

Status: candidate, not built or accepted yet.

r22 boot contains four real SIGSEGVs in the two Dolby Codec2 services. This is
independent of the CamX signal35 diagnostic. Tombstone12 has the ComponentStore
allocation at x19=b400007b41319890, while the virtual RefBase offset used by
incStrong points to x0=b400007b413199a0, 272 bytes beyond that address.
Both stock mains embed operator new(0x108), allocating only 264 bytes before
calling the current libcodec2_hidl@1.0 ComponentStore constructor. The resulting
RefBase is outside the allocation. Later failures occur in HIDL store calls.
Both services eventually restart successfully, which does not establish safe
allocation. Both system and vendor libutils mappings coexist in live and
crashed processes; that observation alone is not a linker-timing root cause.

Device-owned service mains now allocate through the current ComponentStore
header. They retain the original Dolby factories and libraries, 8 HIDL threads,
vndbinder setup, binary paths, init credentials, SELinux domains and HIDL1.0
instances: `dolby` and `default1`. The original programs do not call minijail;
this change preserves that behavior. The original decoder/effect libraries
are unchanged. Each source module overrides its corresponding prebuilt.
Initialization/registration failures return an error and are never reported
as successful service registration.

Required acceptance: build, packaged scope and upstream audit, cold-boot logs
with exact allocation size, both services registered without SIGSEGV, list
components/create interfaces on both stores, and existing audio regression.
Raw evidence is in workspace reports/device/r23-investigation, including the
crash buffer and tombstones12/15. No camera, attention request or image capture
was performed.

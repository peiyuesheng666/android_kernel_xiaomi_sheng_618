# r23 Dolby Codec2 service allocation

Status: built, packaged and flashed; startup allocation fix verified. Video
component lifecycle has an independent unresolved issue (see runtime review).

r22 boot contains four real SIGSEGVs in the two Dolby Codec2 services. This is
independent of the CamX signal35 diagnostic. Tombstone12 has the ComponentStore
allocation at x19=b400007b41319890, while the virtual RefBase offset used by
incStrong points to x0=b400007b413199a0, 272 bytes beyond that address.
Both stock mains embed operator new(0x108), allocating only 264 bytes before
calling the current libcodec2_hidl@1.0 ComponentStore constructor. The resulting
RefBase is outside the allocation. Later failures occur in HIDL store calls.
The current compiled framework's DWARF confirms DW_AT_byte_size=0x0120 (288),
24 bytes larger than the stock allocation. Raw output is retained in
reports/device/r23-investigation/component-store-dwarf.txt.
Both services eventually restart successfully, which does not establish safe
allocation. Both system and vendor libutils mappings coexist in live and
crashed processes; that observation alone is not a linker-timing root cause.

Device-owned service mains now allocate through the current ComponentStore
header. They retain the original Dolby factories and libraries, 8 HIDL threads,
vndbinder setup, binary paths, init credentials, SELinux domains and HIDL1.0
instances: `dolby` and `default1`. The original programs do not call minijail;
this change preserves that behavior. The original decoder/effect libraries
are unchanged. Each source module is non-installable, and the device extraction
postprocessor attaches its output to the original vendor prebuilt. There is
exactly one installer for each original binary path. The first build exposed
a duplicate-install rule when package overrides were used; it failed before
compilation and no image was flashed. That attempted wiring is superseded.
Initialization/registration failures return an error and are never reported
as successful service registration.

The second build compiled and linked both device mains and passed the install
rule stage. Its final prebuilt ELF check rejected two undeclared dependencies
exported by the current Codec2 defaults: server_configurable_flags and
libaconfig_storage_read_api_cc. Both libraries already exist on the installed
r22 vendor image. The extraction hook now declares them on the two original
installers without disabling ELF checks. This build failure and the first
duplicate-install failure are retained; neither attempt was flashed.

Both newly linked source executables have additionally passed check_elf_file
against libraries pulled from the installed r22 device, not just the rebuilt
library outputs. This checks that the scoped service replacement does not
require an unshipped dependency or symbol. Raw results and exact library hashes
are in live-elf-check.json and live-libraries-sha256.json under the investigation
directory. Both final installed build outputs match these reviewed ELFs.
The third build completed successfully, including both prebuilt ELF checks.
Disassembly confirms both mains allocate 0x120 (288) bytes. Prebuild fresh-fetch
and postbuild physical checks passed for 19 public repositories; all 1243
manifest projects were clean. Windows and WSL device sources were byte-equal.

ShengCodec2HalProbe.cpp is a temporary direct HIDL client. It checks both
original service names, listComponents and createInterface for each reported
component; it never configures, starts or feeds a codec. Its builder reuses the
compiled device service's compiler/linker flags in a separate diagnostic output
directory. The probe has compiled, linked and passed the same live-library ELF
check. It was not run on the unsafe r22 allocation. On r23, both stores passed
listing and all five interface creations. The Java client path allocated four
audio decoders and one video decoder; the subsequent lifecycle checks exposed
an unresolved video issue documented in r23-runtime-20261107.md. Routine checks
now allocate only audio decoders, preserving the video diagnostic failures.

Build, packaged scope, upstream audits, installed partition hashes, both service
interfaces and the user's ordinary audio regression passed. Initial registration
size messages were not retained for both services in the rolling main log;
allocation size is established by installed ELF hashes matching the reviewed
288-byte disassembly. No new SIGSEGV was observed. Two explicit diagnostic
service restarts cleared video allocation/release residues and are not counted
as a lifecycle fix. Final cleanup left both service CPU counters unchanged.
Raw evidence is in workspace reports/device/r23-investigation and the three
r23 runtime directories indexed by runtime-r23-codec2-aon-20261107.json. No
agent camera, attention request or image capture was performed.

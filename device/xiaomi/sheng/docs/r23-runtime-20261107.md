# r23：AON 配置路径与 Dolby Codec2 启动分配

2026-11-07，类原生平板 ca10ede3，b 槽。仅刷 vendor、vbmeta，六分区回读
全部匹配；没有清数据或切槽，另一台官方系统平板未操作。所有实现仍在设备树。

AON 已验收。恢复原厂 `/vendor/lib64/camera/aon_front.pb` 到 ODM 的绝对链接，
目标 8983 字节及 SHA256 保持原厂值。新启动的既存 CamX 文本记录出现
QSEEAONSensorInit success 和检测回调 Event Received: 0，原先的初始化 error1、
管线 finalization/StreamOn 失败不再出现。用户明确确认“aon好了”。保持
adaptive_sleep=1、超时 15000 ms。没有由代理发起相机、检测、拍摄或 provider 重启。

Dolby 服务启动分配越界根因已修正。两个原厂 main 固定分配 264 字节，而当前
ComponentStore 需要 288 字节。设备自有 main 按当前头文件分配；反汇编确认
两个实际 new 参数均为 0x120，实机程序哈希与审核输出一致。两个 HIDL 实例
均能枚举组件，五个组件接口全部创建成功。初始启动及诊断中未见新 SIGSEGV。
首次进程 PID 为 dolby=1373、default1=1382；没有因启动崩溃发生自动恢复。

五个非 secure 解码器的 MediaCodec 分配/释放调用均返回成功：AC4、AC3、EAC3、
EAC3-JOC 和 Dolby Vision HEVC。此结果只验证分配和调用返回，未输入媒体数据，
也不证明完整解码及释放后的线程状态正常。

压力检查另发现未解决的视频组件问题：编码器 c2.dolby.encoder.hevc 创建超过
30 秒未返回；随后只检查解码器，调用虽然返回，视频服务仍留下高 CPU ALooper。
原始栈分别保存在第一次和第二次运行目录。第一次全组件 Java 探针超时不是
通过；旧探针 JAR、原始结果和栈均保留。诊断工具后来增加 decoder-only 模式，
保留错误输出，并将“组件分配成功”和“生命周期正常”分别记录，不能把它们混同。
尚未定位全部运行期根因，视频编解码整体不列为正常。
最终常规验证只分配四个音频解码器，视频仅检查接口；四项分配、释放均通过。
视频组件压力测试必须单独调查，不能再作为默认回归流程反复触发。

为清理测试副作用，提前告知用户后，仅通过 ctl.restart 重启 dolbycodec2
两次，没有重启相机或系统。最终视频服务 PID=10381，音频服务仍为1382。
清理后两次采样之间，两进程 CPU tick 增量均为0，临时探针文件全部删除。
服务重启是诊断清理动作，不能作为持久修复的视频生命周期问题。

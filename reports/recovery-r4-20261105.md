# r3 actual capture and r4 repair

## Latest user evidence supersedes earlier broad failure wording

- User retested the source kernel and reports successful boot with version5.15.220 shown in the system. Record this as user-confirmed kernel boot, not proof that the entire new LineageOS ROM or every peripheral works. Which installed Android userspace was used has not yet been confirmed.
- User now suspects Recovery starts but display is broken; reports black screen with backlight. Do not continue calling the source kernel unbootable or assert all of the earlier apparent fastboot failures were kernel failures.
- During r3's diagnostic hold before Android init, a black display is not evidence of Recovery UI failure. The actual handoff stage must be established from logs.

## Captured evidence

- Windows COM6 enumerated as USB VID1D6B/PID0104, serialSHENG-DIAG-R3, statusOK. This verifies the software USB serial transport on the actual tablet, not just in QEMU.
- First collector PID16088/session41137 captured kernel records starting22:54:50 into reports/serial/sheng-r3-20261105-224743.log. Own diagnostic /dev/kmsg markers/HOLD were absent, so its automatic GO correctly did not fire.
- A verified handoff was explicitly requested through the defined GO command. Old collector was stopped by exact verified PID, then PID47136/session20124 started with -ContinueNow at22:56:59. At22:57:04 it sentGO. Log reports/serial/sheng-r3-20261105-225659.log captured:
  init: mount("sysfs", "/sys", "sysfs",0,NULL) failed Device or resource busy
  init: Init encountered errors starting first stage, aborting
  init: InitFatalReboot: signal6
  init: Reboot ending, jumping to kernel
- Thus this particular r3 reset was introduced by the diagnostic pre-init's duplicate sysfs mount. It is not evidence that the original normal Recovery or source kernel cannot boot. We explained the diagnostic error directly and corrected it without editing platform init.
- Earlier log binds display to qcom,mdss_dsi_visionox_r66451_fhd_plus_video, not this tablet's expected display. r3's direct module bootstrap did not forward runtime module options from the bootloader; it only forwarded options present at image-generation time. This can make msm_drm choose its default panel. The actual bootloader option remains to be observed in the repaired diagnostic record; do not invent a panel name or hardcode another device's panel.
- Touch driver repeatedly reloaded firmware and emitted CRC/reset messages. Preserve this evidence, but do not choose a different firmware without correlating mode/panel/input configuration.
- The referenced TWRP tree's DTB hash equals our supplied stock DTB409d703c291bbe4006c29918c0b71dfdcbddecbd1bdec90d1a4729109f3cd5a3. No other developer's DTB was adopted.

## r4 changes and checks

- Own pre-init detaches its /sys and /proc mounts immediately before exec into Lineage init. Logger keeps open kernel/serial descriptors; configfs remains mounted independently at /config. No changes to platform init or blanket SELinux disabling.
- Own runtime module option parser reads the full actual /proc/cmdline for each module, canonicalizes hyphens/underscores, preserves quoted values and module-specific options, and falls back to image-generated parameters only when no matching runtime option exists.
- Native self-test exercises bootloader panel parameter, normalized names/quoted values, mtdoops.mtddev and fallback. AArch64 QEMU self-test and actual494667-byte PTY/GO transport test pass. Native stage messages now go through a nonblocking pipe to the early serial logger as well as kmsg, so the HOLD record is available independently of stock user-kmsg behavior.
- artifacts/recovery-sheng-lineage-24.0-r4-serial/lineage-24.0-sheng-recovery-r4-serial.img,100MiB, SHA256f7387c1d24826cf86e64f6db35372cee752c09834362c8f48f88dd7b50cc76d9. AVB and Windows read-back SHA pass; stock kernel/DTB/DTBO exactly match r2. r3 artifact is preserved, not silently overwritten.
- New default collector started after stopping verified old PID47136. Do not keep -ContinueNow as the default: the new native HOLD pipe should drive the normal handshake. Actual PID/log/state are in reports/serial/capture-state.json; no duplicate reader should open COM6.

If post-policy logger permissions become a problem, use observed denials to add a scoped recovery diagnostic service/policy; do not disable production SELinux blindly.
